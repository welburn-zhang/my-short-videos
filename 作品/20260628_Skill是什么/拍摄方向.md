# C22A｜什么是 Skill

## 拍摄定位

- **系列位置**：Codex 官方最佳实践第 5 条的上半部分，先讲 Skill，MCP 单独放到下一条。
- **视频主题**：什么是 Skill。
- **核心承诺**：一条视频带用户完整了解 Skill，包括什么是 Skill、怎么获取 Skill、怎么用一个真实案例改造 Skill，最后再推荐一些热门 Skill。
- **核心问题**：当你反复让 AI 做同一类任务时，不应该每次都从头解释要求，而是把固定做法沉淀成 Skill。
- **一句话方向**：Skill 就是给 AI 的工作说明书，把你的流程、标准和判断口径写进去，让 AI 在相似任务里稳定执行。

## 开篇方向

- 开篇可以直接讲清楚：这是一条 Skill 入门总览，会讲「什么是 Skill、怎么获取 Skill、如何改造一个 Skill、以及有哪些热门 Skill 值得关注」。
- 但不要只做课程目录，最好马上接一个用户问题：如果你经常让 AI 做同一类事情，但每次都要重新解释格式、风格、规范和检查标准，那你就该了解 Skill。
- 开头 15 秒内要让用户知道：
  - 这条不是单纯介绍一个工具名，而是解释 Skill 这个能力。
  - 看完之后知道去哪里找、怎么选、怎么改成自己的。
  - 后面会有一个可见的前后对比案例。

## 正片结构

### 1. 什么是 Skill

- 先用普通话解释：Skill 不是神秘插件，而是一份给 AI 的工作说明书。
- 重点讲清三层：
  - **流程**：这类任务应该先做什么、后做什么。
  - **标准**：输出要符合什么格式、什么风格、什么质量要求。
  - **边界**：哪些事不能乱做，哪些结果必须让人检查。
- 观众能带走的判断：凡是你一周内重复做 3 次以上，而且每次要求差不多的事，都值得考虑做成 Skill。

### 2. 如何获取 Skill

- **公开资源**：可以去 skills.sh、Skill Hub、代码托管平台或别人整理的 Skill 集合里找现成案例。
  - skills.sh：适合看最近趋势、热榜、安装量和社区关注度。
  - Skill Hub：适合按不同使用场景找，比如开发、写作、设计、研究等。
  - 代码托管平台和公开集合：适合找更具体、更细分的业务案例。
- **工具辅助查找**：安装或调用类似 Find Skills 的 Skill，把自己的需求描述给它，让它去全网搜索相近的 Skill，并给出候选推荐。
- **自己编写**：用 Codex 内置的 `$skill-creator`，或手动写一个 `SKILL.md`。
- **推荐方式**：找一个和自己业务场景相近的 Skill，再按自己的资料、口径、流程和输出格式改掉。
- 口播里可以强调：不要一上来追求从零写，先借一个相似的，再改成自己的，这更像普通人真正能上手的方式。

### 3. 操作演示

- **主演示案例**：用 UI/UX Pro Max 这类设计 Skill / Base Scale 生成一个前端活动页，再把它改造成符合企业内部设计规范的专属 Skill / Scale。
- 演示逻辑：
  1. 先用基础设计 Skill / Base Scale 生成一个活动页。
  2. 展示第一版问题：页面可能通用好看，但不像企业级项目，不符合品牌色、字体、字号、间距、圆角和组件规范。
  3. 给 AI 补充企业内部设计规范，包括字体、字号、间距、圆角、颜色、按钮样式、卡片样式、移动端适配等。
  4. 让 Codex 基于这些规范改造原来的 Base Skill / Scale。
  5. 再生成一次活动页，做前后对比：第一版是通用好看，第二版是符合品牌规范、可以在企业内部复用。
- 演示的核心结论：Skill 的价值不是直接套一个现成模板，而是把你的工作标准写进去，让 AI 后续自动按这套标准干活。
- 口播口径建议：画面里可以出现 Scale，但嘴上尽量讲「基础设计 Skill」「专属设计 Skill」「团队设计规范」，避免普通观众被 Scale 这个词卡住。

### 4. 热门 Skill 推荐

- 不做大清单，按场景推荐更容易让观众记住。
- 可以按这几类讲：
  - **搜索类**：Find Skills，用来根据需求找候选 Skill。
  - **开发类**：Superpowers，用来辅助代码、工程和项目操作。
  - **写作 / 研究类**：Content Research，用来做资料整理、内容研究和结构化输出。
  - **设计类**：UI/UX Pro、UI/UX Pro Max，用来做界面、页面和设计规范相关任务。
- 热门 Skill 的具体名称和热度，写正式脚本前需要再核实一遍，避免推荐过时或名称不准确。

## 需要注意的点

- 不要把 Skill 讲成「万能插件」或「神秘技能包」，它的重点是流程复用。
- 不要做成 Skill 网站清单，也不要讲成热门 Skill 报菜名。
- 不要演示账号登录、下载安装、外网入口和复杂环境配置。
- 如果提到公开资源和代码托管平台，重点说「找相似案例，再改成自己的」，不要把教程拍成入口教学。
- Find Skills 类工具只能作为初筛，不能找到什么就直接装什么；要看清来源、说明、脚本内容和权限边界。
- 设计演示不要变成前端炫技，重点放在「第一版问题、补充规范、改造后复用」。
- 企业设计规范建议用虚拟品牌或脱敏参数，不展示真实公司内部信息。
- 和 MCP 的边界只用一句话交代：Skill 教 AI 怎么做，MCP 让 AI 去连接真实资料和工具，下一条再讲 MCP。
